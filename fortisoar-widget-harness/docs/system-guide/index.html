SOC Assistant System Guide

How the widget, the connector, the fsr_playbooks library and the build and deploy tooling fit together. For each part: what it does, how it decides, what keeps it safe, and why it was built that way. File references are to the working trees on the build Mac.

00The map

The product line is "AI finds the pattern. A playbook runs it forever." It makes four promises:

  • P1 Investigate a record and return a verdict where every finding cites the tool call it came from.
  • P2 Propose containment actions that a human approves, gated by risk tier.
  • P3 Reach on-prem targets through the analyst's chosen connector config.
  • P4 Bottle an investigation, or a request, into a FortiSOAR playbook that runs without the AI.

Four pieces deliver it. The widget is the window; the connector is the engine; fsr_playbooks is the brain's rulebook; the harness is how we build and ship all of it.

Who decides what

This is the one idea to hold onto. The model proposes. Deterministic code checks. A human commits.

The model

  • Reads the request
  • Picks tools, connectors, operations
  • Drafts YAML or edit operations
  • Reacts to fix lists
  • Writes the prose and the verdict

The code

  • Which tools exist this turn
  • Whether each call is allowed
  • Whether a playbook compiles and verifies
  • Which exact bytes can be offered
  • Whether a save would lose data
  • Risk tier of every action

The analyst

  • Clicks Apply or Save on a playbook
  • Confirms each tier 3 or 4 action
  • Answers choice and manual-input cards
  • Reviewers own the autonomy policy

01One turn, end to end

Every interaction is a "turn". The widget never waits on a long HTTP request. It starts the turn detached and then polls for progress, because FortiSOAR's uWSGI workers kill requests after a few minutes and a playbook build can take longer.

  1. Widget sends the whole conversation. _runTurnNow sends chat_turn with every prior message (old tool results capped at 2048 chars), the page facts, the record or open playbook as entity, and detached:true. The connector builds model context from messages[] only. It never reads its own store back as context. view.controller.js:3947
  2. Connector prepares the turn. It works out the intent (an explicit intent wins, otherwise page facts decide), loads the persona from the Key Store, lets the persona choose a model, warms the connector catalog if cold, and reserves a turn number atomically. ops_chat.py:252-401
  3. Connector plans the turn. plan_turn builds a TurnPlan from structural state: is a playbook open, is there a trace, which page. The plan sets the prompt layers and the refusal rules for this turn. turn_plan.py:438, ops_turn_state.py:459
  4. The agent loop runs. One shared run_loop serves every LLM provider. Each round, the model returns text and tool calls. Each call passes the gates before it runs, and calls in a round run in parallel up to the first that needs approval. agent_loop.py:325, 801-842
  5. Frames stream back. Every event is written as a frame to the turn_progress table. The widget polls chat_poll every 700 ms and renders a live preview. A heartbeat thread marks the turn alive; a turn silent for 420 s is failed rather than left hanging.
  6. The turn ends in a card. A triage ends in a verdict card and maybe an action card. A build ends in a playbook offer or an enhancement offer. If the model verified a playbook but forgot to deliver it, the loop delivers the offer itself. If the turn still ends without one, the connector salvages an offer from the last YAML block or the last verified draft. agent_loop.py:688-716, ops_offers.py:96-245
  7. The analyst answers the card. Buttons send chat_resume. The connector routes on the stored card (never on what the browser claims) and runs the decision once. ops_resume.py:50
Frame types and resume calls

Frames: text, tool_use, tool_result, usage, activity, approval_request, error, the card events (action, choice, capability_gap, manual_input, playbook_offer, enhancement_offer, verdict, info, ioc, status), turn_start and stream_end. Wire contract version 2.8.0; the widget banners a major mismatch.

Resume calls: approval (carries approval_id), choice (choice_id, value), action card (card_id, args, grant, config), offer (offer_id, title, edits, workflow_iri, apply_to), and manual input (respond_manual_input, which resumes a paused FortiSOAR playbook run).

History: the last 4 turns replay as real tool_use/tool_result pairs. Collapsing history into text like "[called x(...)]" taught the model to type tool calls as text in 3 of 4 runs, so it was replaced.

02The playbook builder

In one paragraph The LLM never writes FortiSOAR JSON and never saves anything. It drafts a small, friendly YAML format. The fsr_playbooks library compiles that YAML against a catalog of the box's real connectors, operations and modules, then verifies it: compile, a typed walk of every path, per-step schema checks, an offline walk of every branch, and an inventory of what the playbook changes. A passing draft gets a content hash, the verified_id, and only those exact bytes can reach an offer card. The save happens in the connector, only when the analyst clicks Apply, after diffing against the live playbook, refusing any unacknowledged loss and taking a snapshot. The model supplies intent and drafting. The library supplies correctness and safety.

The build loop

  1. Read what is open. In the designer, the widget calls decompile_playbook at mount and sends the playbook as YAML with every turn. The next turn always edits the current draft.
  2. Discover. The model calls find (one entry point for connectors, operations, examples, recipes, fields, Jinja) and get_op_schema for parameters and the known output shape. Answers come from the reference catalog, which is warmed from the box, so it only sees connectors that exist.
  3. Draft. For a new playbook, the model writes YAML. For an open playbook, it sends edit_playbook operations: add, update, rename or remove a step; set or remove a route; add or remove a parameter. The tool applies them to the open playbook, so any step the model did not name is carried over untouched.
  4. Verify. verify_playbook (new) or the verify built into edit_playbook (edits) returns ready_to_push plus a structured list of required fixes.
  5. Fix and retry. The model reads the fix list and tries again. Repeating an identical failed call is refused, and a stall detector ends a turn that keeps failing.
  6. Offer. emit_card(enhancement_offer, {verified_id}) for an edit, or emit_card(playbook_offer) for a new playbook, which re-verifies the exact bytes it carries.
  7. Apply. The analyst clicks Apply. The connector compiles the card's stored YAML, checks it against the live playbook with the prewrite guard, snapshots, and saves or stages it into the open canvas as unsaved changes.

How it decides

Intent comes from state, not wording

The TurnPlan reads structure: has_open_playbook, has_trace and page. A playbook is open, so this is an edit turn; creating a second playbook is refused and the model is pointed at edit_playbook. Nothing is open, so edit tools are refused. The house rule, written in docs/GUARDS.md, is "never decide by parsing wording". turn_plan.py:107, 311-345

Prompt layers

  • The intent prompt for build or triage (fsr_playbooks/agent/system_prompt_build.md).
  • A context block of page facts plus a disposition paragraph.
  • A constraints block: round budget, approval tiers, "never dead-end the analyst".
  • The persona or grounding layer, then the invariant house rules, then a note on which log sources are available.

Which tools it sees

The framework registers 77 tools for its MCP server. The agent sees about 26 per turn: 16 framework tools plus the connector's record and triage tools. The list is kept nearly constant so the prompt cache stays warm, then trimmed per turn of anything the plan would refuse (advertised_for_turn). Older docs call this "slicing by intent". The real focusing now comes from the plan's prompt and its dispatch refusals.

On a build turn the record and triage tools (run_op, get_record, record search, SIEM and EDR lookups) are withheld. Everything else the plan might refuse stays listed, so the model learns about a refusal (an offer while a playbook is open, an edit with nothing open) only by calling the tool, which costs a round. The list also changes when a draft becomes the open playbook or a turn is read-only, and that change re-bills the cached prompt prefix at those boundaries. ops_tools.py:96-167, tools.py:1697-1729

The conversation's own draft counts as open

After a build turn offers or saves a playbook, the connector grounds later build turns in the same chat on that draft, so "now also add X" edits it with edit_playbook instead of re-typing it (re-typed refinements once dropped an alert link). The side effect: asking for an unrelated second playbook in the same chat starts as an edit of the first, and a new-playbook offer is refused until the model raises the "modify or create new" choice. A playbook open in the designer always wins over the draft. ops_tools.py:534-577

When it asks instead of acting

Removing steps an analyst did not name brings up a playbook_scope choice card: modify this playbook, or create a new one. Missing inputs become choice or manual-input cards. The constraints block forbids ending on a dead end.

Model choice

One LLMProvider protocol with four providers: anthropic, openai, lmstudio and fortiai-proxy. All share the same loop; capabilities a provider lacks are emulated by the host. The model catalog marks claude-sonnet-5 and gpt-5.4-mini as tested defaults, several Claude models as supported, and haiku-4-5, gpt-4.1-mini and o4-mini as discouraged after measured gate failures. model_catalog.py:62-140

  • With reviewer_roles empty (the default), anyone who can call the op can approve.
  • Claude Code talking to the raw fsr_playbooks MCP server gets all 77 tools with no tier gate. run_op is protected only by confirm=True, which the caller sets.
  • The connector's prewrite guard fails open if an old framework lacks it.

04fsr_playbooks, the library

Most of the system's power is here. The library is a compiler from YAML to FortiSOAR playbook JSON, a reference store describing what exists on a box, and the tools the agent uses. The connector imports it and runs it in process. You can also use it without the agent: the fsrpb CLI, an MCP server for Claude Code, and pyfsr's playbook extra.

The compile pipeline

The core idea Errors are data, not strings. Every check, at every stage, emits a structured diagnostic: a code, a path to the exact step or field, a severity, and often a suggested fix. The compiler never prints. That is what lets the agent read its own fix list and repair the draft, and what lets a human tool show a precise red badge instead of a stack trace. compiler/errors.py

A compile is a fixed sequence of stages. Each stage adds diagnostics to a shared list; a blocking error stops the emit, warnings do not. The order matters: resolve has to run before anything can be type-checked against the catalog, and the graph checks run last because they need the whole resolved playbook.

The YAML step types

Triggers (start, start_on_create, start_on_update, start_on_delete, api_endpoint); logic (set_variable, decision); connector; records (find_record, create_record, update_record, delete_record); human and timing (manual_input, delay, approval, create_task); and others (code_snippet, send_email, workflow_reference, end, ...). Any step can carry when, retry, for_each, ignore_errors and similar modifiers.

Verification beyond compile

Compile proves the playbook is well-formed and every reference exists. Verification goes further and asks whether the data actually flows: does every value a step reads actually get produced upstream, and does every write trace back to something the playbook computed. These checks are the forcing function before a draft can be offered to the analyst.

  • Typed walker: walks the playbook as a DAG, synthesizing the output shape of every step (vars.steps.<step>), accumulating it per branch, and checking every downstream vars.steps.X.y read against the shape that actually exists at that point. Offline and pure: no box, no HTTP, no DB. compiler/typed_walker.py
  • Offline walk (walk_paths): renders the playbook's Jinja locally down the default path and once per decision branch and manual-input option, and reports reads that come out empty. Branches are pinned, so it proves each path is wired, not that a branch fires at runtime. compiler/render_paths.py
  • Effect inventory: lifts every record write and connector action into an inventory and records which upstream steps feed each written value. It flags a verdict or write built only from literals after the playbook computed something real, and a containment playbook with no effect step at all. It proves linkage, not runtime truth; make eval-effect reads the real value back on a box. compiler/effect_inventory.py
  • Grounded output shapes: output shapes measured from real runs, so reads like data.attributes.last_analysis_stats are checked against what VirusTotal actually returns, not a guess. compiler/grounded_shapes.py

Releases and pinning

  • The version comes from the git tag. make release VERSION= requires main, a clean tree and a version above PyPI's, waits for CI, tags, and publishes.
  • The connector pins fsr-playbooks==X in requirements.txt, and that is the only place. At import it asserts the running framework matches the pin.
  • The connector's dev venv uses an editable clone, so it tests whatever branch is checked out. The pre-push CI-mirror hook builds a clean venv from the pin, and that is the real gate.
  • Framework changes reach a box only through a release plus a pin bump, or through ship-dev, which leaves the box reporting the wheel version while running other code.

05The connector

connector-fsr-soc-assistant is a normal FortiSOAR connector with 47 operations. Each op runs synchronously inside FortiSOAR's integration workers and wraps the async framework in asyncio.run(). Lifecycle hooks (start, add config, update config, activate) start a background catalog warmup.

Configuration

  • LLM: llm_provider is anthropic, openai or fortiai-proxy, and each reveals its own key, model and URL fields. persona_models lets a persona pick its own model. simulation_mode serves live tools from simulated data.
  • MCP: mcp_access (all or selected servers), mcp_tier (read-only or mutating), mcp_auth, and a JSON mcp_allowlist escape hatch.
  • Approval: reviewer_roles. Empty means the reviewer gate is off. There is no approval-tier field; the floor is the environment variable FSR_AUTO_APPROVE_READONLY.

State: one SQLite file per host

~/.connector_fsr_soc_assistant.db, one connection per op, 15 s busy timeout, BEGIN IMMEDIATE writes. Main table groups:

  • Chat and streaming: chat_turns, chat_messages, turn_progress (the poll feed), turn_runs (owner and heartbeat), session_transcript.
  • Approvals: suspended_sessions (pickled, 600 s TTL), session_cards, session_card_decisions (decided once), session_card_executions (the source for undo).
  • Resume re-binding: session_intent, session_playbook, session_read_only, session_playbook_scope and similar. A resume often lands on a cold worker with no context, so everything the turn knew is stored and re-bound.
  • Monitor: agent_usage, agent_tool_calls, chat_sessions, scheduled_tasks.

Two approve routes

An approval_id pops a framework gate that suspended mid-tool and continues the loop. A card_id approve on an action card runs run_op deterministically, before the model is involved. Both record the execution, which undo depends on. The deterministic route exists because an approved isolate was once only narrated and never ran.

Autonomy

The policy lives in the Key Store record fsr_autonomy_policy, cached 15 s so the kill switch acts within seconds. Every card gets a "shadow" decision: what the policy would have done. Enforcement needs enabled and mode: enforce, and happens only in unattended auto_triage. In an analyst's chat, cards always wait for a click. Editing the policy requires reviewer_roles.

Undo

undo_action takes the reverse op from the policy or a built-in pair (FortiGate block and unblock), uses the args that actually ran, restores record fields from their prior values, and claims each undo once.

07Autonomy and oversight

Autonomy is how the assistant moves from "proposes, a human clicks" toward "acts on its own" without anyone losing control. It works in three stages, and every stage is visible in the Monitor.

  • Shadow mode is the default. Every card gets a shadow decision: what the policy would have done. Nothing runs without a human.
  • Enforce needs the policy enabled and mode: enforce. It applies only to unattended auto_triage. In an analyst's chat, cards always wait for a click.
  • Earning it: the Monitor states that a rule can be enforced only after two weeks with no "would run it, rejected". In those cases the policy would have acted and a human disagreed.
  • Kill switch: the policy is a Key Store record cached for 15 seconds, so turning it off takes effect within seconds.
  • Who can change it: saving a policy requires a configured reviewer_roles list. The JSON is validated by the framework's policy parser, and an invalid policy is refused with nothing changed.

Each decision is claimed once in the connector's store, so a double click or a second tab cannot run a write twice. The execution record stores the arguments that actually ran, which is what undo reverses.

The root repo fsr_all_widgets is the dev kit: the Makefile, scripts/, the knowledge base, the template, and the harness. Each widget under widgets-src/ is its own git repo. Commit inside the widget's repo, not the root.

What the harness adds

  • Dev server on :14400 that renders widgets inside the real FortiSOAR app shell and proxies /api/* to a lab box.

11Demo questions, with answers

What stops the AI from deleting steps from my playbook?

Four layers. Edits are operations that name only what changes, so other steps are carried over untouched. Verify treats a dropped step as an error unless the analyst named that step and asked for a deletion. At save, the prewrite guard diffs against the live playbook and refuses any loss not acknowledged by the verify verdict, and the AI cannot add acknowledgements. A Versions snapshot is taken before every save.

How do you know the playbook it built works?

Before it is offered, it compiles against this box's real connector catalog, passes a typed check of every variable read on every path, passes per-step schema checks, and is walked offline down every branch to find empty reads. Safe read-only operations can be called live to confirm output shapes. Static checks cannot prove what happens at runtime, so the effect read-back eval runs a playbook on a box and checks the written value.

What if the model invents a connector or operation?

Compile fails with unknown_connector or unknown_operation and a near-match suggestion. A playbook offer is refused if it uses a connector not configured on the box. An approval card is never raised for an operation that does not exist.

Why not let the LLM write FortiSOAR JSON directly?

It is verbose, full of UUIDs and internal IRIs, and there is nothing to check it against. The YAML format is compact, the compiler resolves it against the real catalog, errors come back as structured fix lists the model can act on, and the decompiler turns any live playbook back into YAML for editing.

Can the AI approve its own action?

No. Tiers are assigned by code. An approval flag in a model's tool call is rejected. Suspended sessions are HMAC-signed so a resume cannot be forged, and with reviewer roles configured, only the session's initiator or a reviewer can decide, once.

Is it prompt-steered or code-steered?

Mostly code. The prompt explains the rules so the model spends fewer rounds. Tool availability, refusals, verification, tiers and the save guard are enforced in code whether or not the model followed the prompt.

What if it loops forever?

A turn has at most 40 rounds, a budget warning at 3 left, a stall detector that ends repeated or all-failing rounds, and a refusal of any identical call that already failed.

Which model does it use? Can I use our own?

Any of four providers through one interface: Anthropic, OpenAI-compatible endpoints, LM Studio, or the FortiAI proxy. The tested defaults are Claude Sonnet 5 and GPT-5.4 mini. A persona can pick its own model.

What does the analyst still have to do?

Click Apply or Save on any playbook change and confirm every action that changes data or touches a third-party system. Autonomy can take over tier decisions only in unattended auto-triage, only in enforce mode, under a policy that reviewers own and can switch off within seconds.

How does an investigation become a playbook?

At the end of a triage, the offer lists the steps that actually ran. Accepting runs build_playbook_from_trace, which replays those operations and wires their inputs by matching values. The model does not write any YAML on this path.

12Sharp edges and stale docs

Behaviour to know

  • The action card shows the connector operation id (for example fortinet-fortigate.add_to_address_group) as a de-emphasised technical chip beside the human title. That is deliberate and covered by tests. The editable parameter names are now humanised ("Time to live", not time_to_live), matching the approval card.
  • The approval reviewer gate is off by default (reviewer_roles empty).
  • The raw fsr_playbooks MCP server has no tier gate. Claude Code connected to it can push playbooks directly.
  • op_safety is empty in both local DBs, so offline tiering leans on op category and verbs. A box warmup fills it.
  • verified_id lives in one process, capped at 32. A worker recycle between verify and Apply fails with unknown_verified_id.
  • Per-worker caches (MCP servers, persona, roles, policy) mean behaviour can depend on which worker answers.
  • The connector's SQLite store is per host and reportedly wiped on upgrade.
  • Stop in the chat only stops the browser; the server finishes the turn.
  • The designer integration reaches into FortiSOAR UI internals, so a FortiSOAR UI change can break Apply. It logs designer_stage_failed.
  • After any redeploy, analysts must hard-refresh.
  • The connector's offer salvage ignores read-only turns, so an explain turn that prints a changed, verifying YAML block can still get an Apply card. The store shows explain turns that edited or offered (13 of about 200).
  • An unrelated second playbook asked for in the same chat is treated as an edit of the first one's draft until the model raises the scope choice.
  • The build-only tool list exists twice, in the framework (intents.py) and the connector (ops_prompts.py), and the two already differ.
  • Number and password fields on an action card painted white text on a white background under dark themes, so an analyst approved a device id they could not read. Fixed on a widget branch, not yet shipped.
  • CI runs Python 3.11; the box runs 3.12.

Deploy traps

  • ship.sh kills anything on :14400, including your make dev.
  • ship-verify bumps by default and still defaults SHIP_ENV to .env.
  • A red ship-verify does not mean "not shipped": step 5 deploys before step 6 can fail.
  • make push defaults to a hardcoded box and is not committed yet.
  • widget.js ignores WIDGETS_SRC, so lint, bump and rename from a worktree hit the shared checkout.
  • A dev-patched box reports the wheel version while running other code.

Docs that are wrong today

  • widgets.manifest lists an old widget name and misses fortiaiAgenticAssistant, so make setup on a fresh Mac will not reproduce the current set.
  • The Monitor widget keeps a second hardcoded copy of the connector name, and its info.json claims it reads llm_activity_logs, which it does not.
  • Connector info.json still says "Stub in 0.0.1" for chat_turn; health_check mentions only Anthropic; the audit log hardcodes provider "anthropic".
  • The chat widget README pins two different connector versions; both widgets declare compatibility 7.6.5 while the docs say 8.0.
  • Framework README says "~16 tools" (that is the agent slice; the server has 77). ARCHITECTURE_AGENT_LOOP.md described a loop inside each provider, tool slicing by intent, and collapsed history; a rewrite matching the shared loop is on a framework branch, not merged.
  • Two guard docstrings lag their code: CreateDeliveryGuard still describes a pinned model round (the loop now delivers directly), and VerdictDeliveryGuard says triage-only.
  • The technical deck's generated pptx is current with its script, but some of its asset screenshots are still from an older widget build.
  • STATUS.md has been idle since August; the tracker's ROADMAP.md is the live plan.

An agentic flow that mirrors the playbook builder

  1. Typed spec. A pydantic ConnectorSpec (operations, params, config fields) limited to what the importer accepts. This plays the role the YAML DSL plays for playbooks. Enhancing an existing connector means reading its info.json back into a spec, like the decompiler.
  2. Generate. info.json and operations.py stubs from the spec, with a shared request helper and a drift check. Inputs can be an OpenAPI spec, corpus endpoints, or an existing connector.
  3. verify_connector tool. Spec validation, toolkit lint and anti-patterns, pyfsr importer validation, output schemas against recorded bodies, and a secret scan, returned as structured fix codes the agent can act on, like verify_playbook.
  4. Offline test. Scaffolded tests plus replay against recorded responses in a sandbox. No key, no box.
  5. Human approval. The spec diff, code diff, verify report and test results on a card. Write or disrupt operations need approval before any live run.
  6. Install and prove. Pack, install, configure, health-check, run read-tier operations, record the responses as fixtures, then register it in the reference DB so the playbook builder can use the new connector immediately.

Gaps to close first: one shared typed model for info.json, a Python scaffolder, a single record and replay format, packaging the toolkit, and agent tools for verify, test and install.
